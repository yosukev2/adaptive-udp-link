# MCU UART Packet Format v1

## Purpose

This document fixes the PC-to-MCU UART packet format used by the MCU UART Link Control Demo. PC harnesses, MCU parsers, CRC checks, ACK/NACK handling, telemetry, and later fault-injection tests must use this spec.

## Byte Order

All multi-byte integers are encoded in network byte order, big-endian.

## Packet Layout

| Offset | Size | Field | Type | Description |
|-------:|-----:|-------|------|-------------|
| 0 | 4 | `preamble` | `uint32` | Packet boundary marker, fixed `0xA55AC33C` |
| 4 | 1 | `version` | `uint8` | Protocol version, fixed `1` |
| 5 | 1 | `type` | `uint8` | Packet type |
| 6 | 4 | `seq` | `uint32` | Monotonic sequence number within a trial |
| 10 | 2 | `length` | `uint16` | Payload length in bytes |
| 12 | 4 | `crc32` | `uint32` | CRC over header fields and payload, excluding `preamble` and `crc32` |
| 16 | N | `payload` | bytes | Variable payload, `N = length` |

Header length is 16 bytes. Maximum payload length is 1024 bytes. Maximum packet length is 1040 bytes.

## Fixed Values

| Item | Value |
|------|-------|
| Preamble | `0xA55AC33C` |
| Version | `1` |
| Header length | 16 bytes |
| Maximum payload length | 1024 bytes |
| CRC algorithm | CRC-32/ISO-HDLC |

## Packet Types

| Name | Value | Direction | Purpose |
|------|------:|-----------|---------|
| `DATA` | `0x01` | PC -> MCU | Test payload packet |
| `ACK` | `0x02` | MCU -> PC | Positive acknowledgement for a valid packet |
| `NACK` | `0x03` | MCU -> PC | Negative acknowledgement with error detail in payload |
| `TELEMETRY` | `0x10` | MCU -> PC | Counter snapshot or event telemetry |
| `HEARTBEAT` | `0x11` | Either | Link liveness probe |
| `ERROR` | `0x7F` | MCU -> PC | Non-recoverable or protocol-level error report |

Unknown packet types are invalid for M0 and must be counted as `invalid_type_count`.

## CRC32

CRC input is the concatenation of these fields in wire order:

```text
version || type || seq || length || payload
```

CRC input fixed header length is 8 bytes before payload.

Excluded fields:

- `preamble`
- `crc32`

CRC parameters:

| Item | Value |
|------|-------|
| Polynomial, reflected | `0xEDB88320` |
| Initial value | `0xFFFFFFFF` |
| Final XOR | `0xFFFFFFFF` |
| Bit order | LSB-first, reflected |

The CRC is encoded as a big-endian `uint32` after calculation.

## Sequence Rules

- `seq` starts at 0 by default for each trial.
- PC increments `seq` by 1 for each `DATA` packet.
- MCU ACK/NACK should echo the `seq` of the packet being acknowledged.
- Wrap-around at `2^32` is not part of M0 acceptance testing.
- A packet with the same `seq` as an already accepted packet increments `duplicate_count`.
- A packet with `seq` greater than the next expected value increments `seq_gap_count` by the missing count.

## Valid Packet Example

`DATA`, `seq=1`, payload ASCII `hello`:

| Field | Hex |
|-------|-----|
| `preamble` | `A5 5A C3 3C` |
| `version` | `01` |
| `type` | `01` |
| `seq` | `00 00 00 01` |
| `length` | `00 05` |
| `crc32` | generated over `01 01 00 00 00 01 00 05 68 65 6C 6C 6F` |
| `payload` | `68 65 6C 6C 6F` |

The complete packet is:

```text
A5 5A C3 3C 01 01 00 00 00 01 00 05 <crc32:4> 68 65 6C 6C 6F
```

The exact CRC value should be generated by the shared packet builder used by the PC harness and MCU tests.

## Invalid Packet Examples

| Case | Example | Receiver action | Counter |
|------|---------|-----------------|---------|
| Wrong preamble | `00 00 00 00 ...` | Drop bytes until next preamble candidate | `preamble_miss_count` |
| Unsupported version | `version=2` | Drop packet | `invalid_version_count` |
| Unknown type | `type=0x55` | Drop packet or NACK | `invalid_type_count` |
| Length too large | `length=2048` | Drop packet and resync | `length_error_count` |
| Truncated payload | header says 16 bytes but fewer received | Wait until timeout, then drop partial packet | `timeout_count` |
| CRC mismatch | Payload bit flipped | Drop packet or NACK | `crc_error_count` |
| Duplicate sequence | Two accepted packets with same `seq` | Accept policy-dependent, count duplicate | `duplicate_count` |

## Stream Parsing Rules

UART is a byte stream, so packet boundaries must be recovered by parser state:

1. Search for the 4-byte preamble.
2. Read the fixed 16-byte header.
3. Reject immediately if `version`, `type`, or `length` is invalid.
4. Read exactly `length` payload bytes.
5. Recalculate CRC over `version,type,seq,length,payload`.
6. Accept only if CRC matches.

On invalid header or CRC, the parser resumes preamble search at the next byte after the first byte of the rejected candidate. This avoids getting stuck on corrupted length values.

## Payload Rules

For M0 baseline, `DATA` payloads are printable ASCII strings padded or truncated to the requested payload length by the PC harness. Future binary payloads are allowed as long as `length <= 1024` and the CRC covers the exact bytes on wire.
