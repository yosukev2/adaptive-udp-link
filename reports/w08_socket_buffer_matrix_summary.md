# W08 #131 socket buffer matrix summary

## 結論

- #131 では `SO_RCVBUF` の requested 値を変え、send interval / rate_hz と組み合わせて latency と missing を確認した。
- 実行済みは合計 84 runs。内訳は lowbuf matrix 54 runs、tiny sweep 30 runs。すべて `run_validity=ok`。
- `getsockopt()` の actual は requested と一致しない。`100 / 512 / 1024` はすべて `actual=2304` に丸められ、`4096` 以上は概ね requested の2倍になった。
- 今回の tiny sweep では `rate_hz=14000` でも #130 の大きな missing は再現しなかった。したがって、#130 の missing 増大を「受信bufferが8192未満だったため」とは断定できない。
- 今回の条件では `requested=4096(actual=8192)` 以上で missing はかなり小さい。ただし outlier は残るため、保守的には `requested=16384(actual=32768)` 以上を安定候補として扱うのが妥当。
- CPU 指標は今回取り込んだ成果物には含めていない。判断対象は `rx_by_1recv` CSV の latency / missing と `run_metadata.md` の actual buffer / status。

## 実験条件

- 対象: `SO_RCVBUF`
- 共通固定条件: loopback `127.0.0.1:9000`, payload_len `48`, tx 10 sec, rx 12 sec, recovery_mode `fsm`, CPU affinity none, SO_SNDBUF default
- tiny sweep: rate_hz `10000 / 14000`, requested rcvbuf `100 / 512 / 1024 / 4096 / 8000`, 3 trials
- lowbuf matrix: rate_hz `10000 / 14000 / 18000`, requested rcvbuf `8192 / 16384 / 32768 / 49152 / 65536 / 98304`, 3 trials

## 解釈

- `SO_RCVBUF` は指定値そのものではなく、kernel により最小値・内部管理分を含む actual 値に変換される。今回の最小 actual は `2304`。
- `rate_hz=14000` で buffer を `actual=2304` まで小さくしても missing は平均 3〜28 程度で、#130 の大きな missing とは桁が合わない。
- よって #130 と #131 の差は、単純な buffer size だけでは説明できない。実行時のスケジューリング、ログ取得条件、run間の揺らぎ、または #130 側の別条件差を疑うべき。
- latency の p95/p99 は大きく崩れていない。一方で max latency には outlier があり、tail latency の評価では平均だけでなく max/p99 を併記する必要がある。
