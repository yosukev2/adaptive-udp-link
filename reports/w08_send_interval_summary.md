# W08 send interval sweep summary

## 現象と示唆

* 現象: 50 Hz から 100,000 Hz までは `missing_delta_total=0` で、mean / p95 / p99 latency も安定している。さらに、`rate_hz` が上がるほど latency は悪化せず、むしろ小さくなる傾向がある。

  示唆: 当初想定していた「高rateほど送受信負荷が増えてlatencyが悪化する」という仮説は、この範囲では支持されない。低rateではrx側が `poll()` でidleに入りやすく、wakeup / scheduling待ちがlatencyに乗り、高rateではrxがidleになりにくいためlatencyが小さく見えている可能性がある。

* 現象: 140,000 Hz 以降で `missing_delta_total` が発生し始める一方、受信できたsampleだけを見ると latency は大きく崩れないrateもある。

  示唆: この領域では「latencyが連続的に悪化する」のではなく、処理能力またはsocket queue容量を超えた分がdropし、seq gapとして観測されている可能性が高い。#131ではrx bufferを大きくした場合に、dropが減る代わりにp95/p99/max latencyが上がるかを確認する。

* 現象: どの `rate_hz` でも、最後の1 datagram相当が `latency_max` の外れ値になりやすい。

  示唆: txが最後のdatagramを送信した直後に終了処理へ入り、そのタイミングでrxの最後の `recvfrom()` がCPU上で待たされている可能性がある。#132ではtx/rxを別coreに固定し、この末尾外れ値が改善するかを確認する。

* 現象: 120,000 Hz では、最後の1 datagramだけでなく、最後の数datagramにまたがって外れ値が出る。

  示唆: 末尾1 datagramだけの遅延とは別に、終了直前にrx queue backlogが複数datagram分発生している可能性がある。同じ原因かどうかは、#132のCPU affinity結果と時系列プロットで確認する。

* 現象: 50,000〜120,000 Hzでは、受信開始直後だけlatencyが大きく、その後は小さく安定する傾向がある。

  示唆: steady-stateの飽和ではなく、tx/rx起動タイミング差、CPU idle復帰、cache/page/CSV I/O初期化などにより、起動直後だけrx socket queueにbacklogができ、その後rxがdrainして追いついている可能性が高い。測定開始前warm-up、先頭N件除外、rx ready後にtx開始する同期方式を検討する。

* 現象: 120,000 Hz は欠落なしだが、tail latency の外れ値が出始めている。

  示唆: 100,000 Hzまでは安定領域、120,000 Hzは安定領域の上限付近または遷移領域として扱うのが妥当である。

* 現象: 500,000 Hz では `missing_delta_total` と p99 latency が明確に悪化する。

  示唆: この条件では処理能力またはsocket queueの限界に入り、飽和側のデータとして扱うべきである。

* 現象: 1,000,000 Hz では実効受信数が期待値から大きく外れる。

  示唆: 送受信が実効上追従できておらず、latency評価以前に測定条件自体が崩れ始めている可能性が高い。

* 現象: 現在のsummaryだけでは、mean / p95 / p99 / max / missing_delta の全体統計は見えるが、latency増加が「受信開始直後」や「終了直前」に偏って発生していることをエージェントが見落としている。特に、max値だけでなく、先頭・末尾の複数datagramにまたがる局所的なlatency増加というタイミング上の示唆がsummaryからは読み取りにくい。

  示唆: CSV全量をエージェントに読ませるのではなく、summary側に `head latency`、`tail latency`、`steady-state latency`、`max_index`、`max_time_sec`、`max_position_ratio`、時間binごとのp95/p99を追加する。加えて、rate_hzごとの時系列プロット画像を残し、エージェントには特徴量と画像を読ませる。


## 固定条件

- loopback: `127.0.0.1`
- port: `9000`
- payload_len: `48`
- tx duration: `10 sec`
- rx duration: `12 sec`
- recovery_mode: `fsm`
- socket buffer tuning: none
- CPU affinity: none

Issue 本文では `run1.csv`〜`run3.csv` を成果物としていたが、今回は send interval sweep と high-rate sweep に拡張した。PR に含める raw evidence は代表安定点と境界点に絞り、1recv ごとの CSV のみを残す。

- 対象 rate: `10000 / 100000 / 120000 / 140000 / 250000`
- 成果物パス: `data/w08/send_interval/raw_logs/{send_interval,send_interval_high}/rate_<hz>_trial<trial>/rx_by_1recv.csv`

## 指標メモ

- `sample_count`: CSV に記録された受信 row 数。
- `effective_rx_hz`: `sample_count / 10 sec`。今回の tx duration は 10 秒。
- `missing_delta_total`: CSV 内で観測された seq gap の合計。高 rate での欠落・取りこぼしを見る。
- `missing_rate`: `missing_delta_total / (last_seq + 1)`。
- `parse_errors`: `parse_status != OK` の合計。
- `rx_cpu_*`: `rx_1sec.csv` の `cpu_pct`。1秒窓の受信 process CPU 使用率。
- `tx_cpu_*`: `tx.log` の `tx_stats ... cpu_pct`。1秒窓の送信 process CPU 使用率。
- latency 系指標は `parse_status=OK` の row から計算する。
